\section{Project Overview}
This laboratory report provides a comprehensive examination of the architecture, design, and implementation of a real-time video streaming application. The developed system operates on a standard client-server paradigm, leveraging the \textbf{Real-Time Streaming Protocol (RTSP)} for stateful control signaling over a reliable TCP connection, and the \textbf{Real-time Transfer Protocol (RTP)} for active media packetization and delivery.

The project addresses core challenges in multimedia communication over IP networks, specifically targeting robust performance and user experience. The key technical features implemented and discussed in this report include:
\begin{enumerate}
    \item \textbf{Control Channel Signalling (RTSP)}: The implementation of a structured, state-machine driven protocol for session control (inclusive of SETUP, PLAY, PAUSE, and TEARDOWN routines).
    \item \textbf{High-Concurrency I/O Multiplexing}: The server architecture has been modernized using a single-threaded, high-performance event loop utilizing Python's \texttt{selectors} module, replacing the traditional thread-per-client model.
    \item \textbf{Media Delivery (RTP)}: The encapsulation of Motion JPEG (MJPEG) frames into standard RTP packets with a compliant 12-byte binary header (including version, payload type, sequence numbers, timestamps, marker bits, and SSRC).
    \item \textbf{UDP Packet Fragmentation}: A robust mechanism for chunking large video frames that exceed the Maximum Transmission Unit (MTU) into multiple RTP sub-packets, with marker-bit-based reassembly on the client.
    \item \textbf{Reliable TCP Transport Mode}: The introduction of \textbf{RTP-over-TCP} streaming. To prevent TCP byte-stream amalgamation, a custom 5-byte frame size header mechanism was engineered, facilitating stable, frame-by-frame transmission without packet loss or sequence reordering.
    \item \textbf{Adaptive Quality Switching with Client-Side Caching}: The development of a dynamic quality toggle (SD $\leftrightarrow$ HD) within the client interface. The client maps SD to UDP transport and HD to TCP transport. A client-side frame buffer with a high/low water mark mechanism reduces jitter during playback, and a draining pipeline ensures seamless transitions when the user triggers a ``Setup Again'' to reset the stream.
\end{enumerate}

\section{RTSP State Machine and Control Signalling}
The Real-Time Streaming Protocol (RTSP) functions as a stateful, out-of-band control protocol. In our implementation, RTSP operates over a reliable TCP channel (binding to an administrator-defined port). The RTSP protocol is responsible for establishing and modifying media sessions through three sequential states: \texttt{INIT}, \texttt{READY}, and \texttt{PLAYING}.

\begin{figure}[H]
\centering
\begin{tikzpicture}[node distance=4cm, auto]
    \node[circle, draw, minimum size=2.5cm, fill=blue!10] (init) {\textbf{INIT}};
    \node[circle, draw, minimum size=2.5cm, fill=green!10, right of=init] (ready) {\textbf{READY}};
    \node[circle, draw, minimum size=2.5cm, fill=red!10, right of=ready] (playing) {\textbf{PLAYING}};
    
    \path[->, >=stealth, thick] 
        (init) edge node[above] {SETUP} (ready)
        (ready) edge[bend left] node[above] {PLAY} (playing)
        (playing) edge[bend left] node[below] {PAUSE} (ready)
        (playing) edge[bend left=45] node[below, yshift=-0.5cm] {TEARDOWN} (init)
        (ready) edge[bend right=45] node[above, yshift=0.5cm] {TEARDOWN} (init);
\end{tikzpicture}
\caption{RTSP Session Control State Machine}
\end{figure}

The text-based RTSP protocol requires strict header parsing. The \texttt{CSeq} (Command Sequence Number) is incremented by one for each sequential request to maintain synchronization. The \texttt{Session} header maintains the transaction binding between the client and server throughout the lifecycle of a streaming session.

\subsection{Extended SETUP for Transport Negotiation}
Our system extends the standard SETUP request to dynamically negotiate the transport protocol. The client determines the transport based on the selected quality: selecting \textbf{SD} maps to \texttt{RTP/UDP}, while selecting \textbf{HD} maps to \texttt{RTP/TCP}. The \texttt{Transport} header is the sole mechanism for this negotiation --- the server reads only this header to determine whether to stream via UDP or TCP:
\begin{lstlisting}[caption=RTSP SETUP request with Transport negotiation]
SETUP movie.Mjpeg RTSP/1.0
CSeq: 1
Transport: RTP/TCP; client_port= 25000
\end{lstlisting}

\subsection{Re-SETUP for Quality Switching}
A distinctive feature of our implementation is that the server accepts \texttt{SETUP} requests from \textbf{any state}, not just \texttt{INIT}. When a \texttt{SETUP} arrives while the server is in \texttt{PLAYING} state, it gracefully stops the current sending thread, closes the existing RTP socket, creates a fresh \texttt{VideoStream} (resetting to frame 0), and transitions back to \texttt{READY}. This enables seamless quality switching without full session teardown.

\section{RTP Packetization and UDP Fragmentation}
The RTP protocol encapsulates video payloads with a standard 12-byte binary header. When utilizing UDP as the underlying transport mechanism, the payload size is strictly constrained by the network's Maximum Transmission Unit (MTU). Standard Ethernet MTU is 1500 bytes. Deducting the IP header (20 bytes) and the UDP header (8 bytes) yields a maximum UDP payload of 1472 bytes. Deducting the 12-byte RTP header gives a maximum safe video payload of 1460 bytes. We conservatively selected \textbf{1400 bytes} as our maximum chunk size (\texttt{MAX\_RTP\_PAYLOAD\_SIZE}).

Since a single MJPEG frame often exceeds this limit (sometimes reaching 6--10 KB), we engineered a fragmentation algorithm:
\begin{enumerate}
    \item \textbf{MTU Fragmentation}: If a raw MJPEG frame exceeds 1400 bytes, the server slices the byte-array into $N$ consecutive chunks using a \texttt{while bytesSent < frameSize} loop.
    \item \textbf{Marker Bit (M)}: The RTP marker bit (bit 8 in the second header byte) plays a crucial role. It is set to \texttt{0} for intermediate chunks and \texttt{1} exclusively for the final chunk of a given frame. This is computed dynamically as \texttt{(bytesSent + chunkSize) == frameSize}.
    \item \textbf{Sequence Numbers}: The RTP sequence number (\texttt{rtpSeq}) is incremented for each individual fragment chunk, not just per frame. This allows the client to identify lost or out-of-order packets at the chunk level.
    \item \textbf{Client Reassembly}: The client constantly reads UDP datagrams, decodes the RTP header, extracts sequence numbers, and appends payloads into a RAM buffer. Upon receiving a packet with a marker bit of \texttt{1}, the client flushes the buffer, joins the segments into a complete JPEG image, and enqueues it into the frame buffer.
\end{enumerate}

\section{Reliable Frame-by-Frame TCP Media Stream}
While UDP is suitable for low-latency, loss-tolerant streams, high-definition (HD) video demands absolute reliability. Over UDP, a single lost chunk corrupts the entire reassembled frame, resulting in visual artifacts. To resolve this, we implemented an \textbf{RTP-over-TCP} media stream.

\textbf{The Framing Problem}: 
TCP is a stream-oriented protocol. It guarantees delivery and order but does not preserve message boundaries. If the server sends two 5KB frames back-to-back, the client's \texttt{recv()} call might read parts of both frames simultaneously, completely corrupting the JPEG decoding process.

\textbf{The Solution}:
We engineered a custom framing protocol. Before transmitting a frame, the server calculates its exact byte length and prepends this length as a \textbf{5-byte zero-padded ASCII string} (e.g., \texttt{"06742"}). The client reads exactly 5 bytes from the socket to determine the payload size, then invokes a specialized \texttt{recv\_all(length)} function to extract exactly that many bytes. This completely bypasses the fragmentation and sequence tracking overhead of UDP, delivering each frame as a single, intact unit.

\subsection{TCP Connection Establishment}
For TCP media delivery, the roles are reversed compared to the control channel: the \textbf{client} acts as the TCP listener (\texttt{socket.listen(1)}) on the RTP port, and the \textbf{server} connects to the client after receiving a \texttt{PLAY} request. The client uses \texttt{SO\_REUSEADDR} to allow rapid port rebinding when switching quality.

\section{Client-Side Caching and Jitter Buffer}
The client-side caching mechanism implements a \textbf{producer-consumer} architecture with a shared frame buffer to decouple network I/O from GUI rendering:

\begin{enumerate}
    \item \textbf{Producer (Network Thread)}: The \texttt{listenRtpWithUDP} or \texttt{listenRtpWithTCP} method runs in a background thread. Instead of directly updating the GUI, it appends complete frames into a shared \texttt{frameBuffer} list (capacity: 100 frames), protected by a \texttt{threading.Lock} (\texttt{bufferLock}).
    \item \textbf{Consumer (GUI Render Loop)}: The \texttt{renderClientBufferLoop} method is scheduled via Tkinter's \texttt{master.after()} mechanism. It pops frames from the buffer at a fixed cadence (every 40ms, approximately 25 fps) and calls \texttt{updateMovie()} to render each frame.
    \item \textbf{High Water Mark}: When the buffer is empty and new playback begins, the consumer enters a \textbf{buffering} state (\texttt{isBuffering = True}). It waits until the buffer accumulates at least \texttt{minBufferSize} (15) frames before beginning to render. This pre-buffering absorbs network jitter and provides a smooth initial playback experience.
    \item \textbf{Low Water Mark / Starvation Recovery}: If the buffer drains to zero during normal playback (\texttt{len(frameBuffer) == 0}), the consumer re-enters the buffering state and waits for the high water mark to be reached again.
\end{enumerate}

\section{Setup Again: Draining Pipeline and Stream Reset}
The ``Setup Again'' feature allows the user to click the \texttt{Setup} button at any point during playback or pause to reset the video stream and choose a new quality. The implementation uses a \textbf{draining pipeline} to ensure a graceful transition:

\begin{enumerate}
    \item \textbf{During PLAYING state}: When the user clicks Setup, the system sets \texttt{pendingSetup = True} and calls \texttt{startDrainingPipeline()}. This signals the network thread to stop (\texttt{playEvent.set()}) and sets \texttt{isDraining = True}. The render loop continues to pop and display remaining buffered frames.
    \item \textbf{Buffer Drain}: The \texttt{renderClientBufferLoop} detects \texttt{isDraining == True} and skips the buffering check, directly consuming frames until the buffer is empty.
    \item \textbf{Transition}: Once the buffer is fully drained, the render loop checks \texttt{pendingSetup}. If true, it resets the client state to \texttt{INIT} and triggers \texttt{chooseQuality()} to display the quality selection dialog.
    \item \textbf{During READY (Paused) state}: The buffer is cleared immediately, state resets to \texttt{INIT}, and the quality dialog appears instantly.
    \item \textbf{Server Re-SETUP}: On the server side, the SETUP handler cleans up any previous session resources (stops old sending thread, closes old RTP socket) and creates a fresh \texttt{VideoStream} from the beginning. The session ID is preserved to avoid breaking the RTSP control channel.
\end{enumerate}

\section{High-Performance Server I/O Multiplexing}
Spawning a separate thread for every connected client is inefficient, leading to context-switching overhead and poor scalability. To support high-concurrency client streams, we refactored \texttt{Server.py} to utilize \textbf{I/O Multiplexing} via Python's \texttt{selectors} module.

\begin{lstlisting}[language=Python, caption=Server.py - Non-blocking Event Loop]
class Server:   
    def __init__(self):
        self.serverWorkers = {}
        self.selectors = selectors.DefaultSelector()
    
    def accept_client(self, rtspSocket):
        try: 
            clientSocket, clientAddress = rtspSocket.accept()
            clientSocket.setblocking(False) # Critical: Non-blocking mode
            clientInfo = {'rtspSocket': (clientSocket, clientAddress)}

            worker = ServerWorker(clientInfo)
            self.serverWorkers[clientSocket] = worker
            # Register the new client socket for read events
            self.selectors.register(clientSocket, selectors.EVENT_READ, 
                                    self.handle_client_request)
        except Exception as e:
            print(f"Error accepting client: {e}")

    def handle_client_request(self, clientSocket):
        worker = self.serverWorkers.get(clientSocket)
        if worker:
            try:
                worker.recvRtspRequest()
            except Exception as e:
                print(f"Cleaning up disconnected client: {e}")
                try:
                    self.selectors.unregister(clientSocket)
                except:
                    pass
                clientSocket.close()
                if clientSocket in self.serverWorkers:
                    del self.serverWorkers[clientSocket]

    def main(self):
        rtspSocket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        rtspSocket.bind(('', SERVER_PORT))
        rtspSocket.listen(5)        
        rtspSocket.setblocking(False)
        self.selectors.register(rtspSocket, selectors.EVENT_READ, 
                                self.accept_client)
        # The Event Loop
        while True:
            events = self.selectors.select()
            for key, mask in events:
                callback = key.data
                callback(key.fileobj)
\end{lstlisting}

The server socket and all incoming client sockets are explicitly set to non-blocking mode (\texttt{setblocking(False)}). The primary server loop halts at \texttt{self.selectors.select()}, waiting for OS-level interrupts indicating readable events. When data arrives, it dispatches the RTSP commands to the appropriate \texttt{ServerWorker} without launching redundant threads.

\subsection{Non-blocking Socket and BlockingIOError Handling}
Because all client sockets operate in non-blocking mode, the \texttt{recvRtspRequest} method in \texttt{ServerWorker.py} must handle \texttt{BlockingIOError}, which is raised when \texttt{recv()} is called on a non-blocking socket with an empty kernel buffer. The exception is silently caught and the method returns, allowing the event loop to continue monitoring other sockets:
\begin{lstlisting}[language=Python, caption=ServerWorker.py - Non-blocking RTSP Reception]
def recvRtspRequest(self):
    connSocket = self.clientInfo['rtspSocket'][0]
    try:
        while True:            
            data = connSocket.recv(256)
            if data:
                self.processRtspRequest(data.decode("utf-8"))
            else:
                raise ConnectionError("Client disconnected")
    except BlockingIOError:
        pass  # No data available yet, return to event loop
\end{lstlisting}

\subsection{Graceful Client Disconnection Cleanup}
When a client disconnects (detected by \texttt{recv()} returning empty bytes or raising a \texttt{ConnectionError}), the exception propagates to \texttt{handle\_client\_request} in \texttt{Server.py}, which performs cleanup: unregistering the socket from the selector, closing the socket, and removing the worker from the dictionary. This prevents stale file descriptors from accumulating.

\section{RTP Packetization and Binary Header Encoding}
The \texttt{RtpPacket.py} module implements the standard 12-byte RTP header encoding according to RFC 1889:

\begin{lstlisting}[language=Python, caption=RtpPacket.py - 12-byte RTP Header Encoding]
def encode(self, version, padding, extension, cc, seqnum, 
           marker, pt, ssrc, payload):
    timestamp = int(time())
    header = bytearray(HEADER_SIZE)

    # Byte 0: V(2) | P(1) | X(1) | CC(4)
    header[0] = (version << 6) | (padding << 5) | \
                (extension << 4) | (cc & 0x0F)                    
    # Byte 1: M(1) | PT(7)
    header[1] = (marker << 7) | (pt & 0x7F)
    # Bytes 2-3: Sequence Number (16-bit, big-endian)
    header[2] = (seqnum >> 8) & 0xFF
    header[3] = seqnum & 0xFF
    # Bytes 4-7: Timestamp (32-bit, big-endian)
    header[4] = (timestamp >> 24) & 0xFF
    header[5] = (timestamp >> 16) & 0xFF
    header[6] = (timestamp >> 8) & 0xFF
    header[7] = timestamp & 0xFF
    # Bytes 8-11: SSRC (32-bit, big-endian)
    header[8] = (ssrc >> 24) & 0xFF
    header[9] = (ssrc >> 16) & 0xFF
    header[10] = (ssrc >> 8) & 0xFF
    header[11] = ssrc & 0xFF

    self.header = header
    self.payload = payload
\end{lstlisting}

The header fields are filled byte-by-byte using bitwise shift and mask operations. Since Python's byte order matches network byte order (big-endian), no additional byte-order transformation is required. The \texttt{decode} method performs the reverse: extracting the 12-byte header and payload from a received byte stream, with accessor methods for \texttt{version()}, \texttt{seqNum()}, \texttt{marker()}, \texttt{timestamp()}, and \texttt{payloadType()}.

\section{UDP Fragmentation Logic}
The \texttt{ServerWorker.py} script manages the fragmentation of large JPEG frames to fit within the UDP MTU constraints:

\begin{lstlisting}[language=Python, caption=ServerWorker.py - UDP Fragmentation with Marker Bit]
def sendRtpWithUDP(self):
    MAX_RTP_PAYLOAD_SIZE = 1400
    while True:
        self.clientInfo['event'].wait(0.05) 
        if self.clientInfo['event'].isSet(): 
            break 
            
        data = self.clientInfo['videoStream'].nextFrame()
        if data: 
            frameSize = len(data)
            bytesSent = 0
            while bytesSent < frameSize:
                chunkSize = min(MAX_RTP_PAYLOAD_SIZE, 
                                frameSize - bytesSent)
                chunkData = data[bytesSent:bytesSent + chunkSize]
                # Marker bit = 1 ONLY for the final chunk
                markerBit = (bytesSent + chunkSize) == frameSize
                
                packet = self.makeRtp(chunkData, self.rtpSeq, 
                                      markerBit)
                self.clientInfo['rtpSocket'].sendto(
                    packet, (address, port))
                    
                self.rtpSeq += 1
                bytesSent += chunkSize
\end{lstlisting}
The \texttt{while bytesSent < frameSize} loop slices the byte array into chunks of at most 1400 bytes. The \texttt{markerBit} is computed dynamically by checking if the current chunk boundary aligns with the total \texttt{frameSize}. This ensures the client can detect frame boundaries even when a single frame is split across many UDP datagrams.

\subsection{Client-Side UDP Reassembly}
On the client side, fragments are reassembled using a temporary buffer that accumulates chunk payloads until the marker bit signals the end of a frame:
\begin{lstlisting}[language=Python, caption=Client.py - UDP Fragment Reassembly]
def listenRtpWithUDP(self):
    buffer = []
    while not self.playEvent.isSet():
        try:
            data = self.rtpSocket.recv(2000)
            if data:
                rtpPacket = RtpPacket()
                rtpPacket.decode(data)
                currSeqNbr = rtpPacket.seqNum()

                if currSeqNbr > self.frameNbr:
                    self.frameNbr = currSeqNbr
                    buffer.append(rtpPacket.getPayload())

                    if rtpPacket.marker() == 1:
                        fullFrame = b''.join(buffer)
                        buffer.clear()
                        with self.bufferLock:
                            self.frameBuffer.append(fullFrame)
                            if len(self.frameBuffer) > 100:
                                self.frameBuffer.pop(0)
        except:
            buffer.clear()
            if self.playEvent.isSet(): break
\end{lstlisting}
Late or out-of-order packets are discarded via the \texttt{currSeqNbr > self.frameNbr} guard. Once the marker bit is detected (\texttt{marker() == 1}), the accumulated chunks are joined with \texttt{b''.join(buffer)} and appended to the shared \texttt{frameBuffer} under lock protection. A hard cap of 100 frames prevents unbounded memory growth.

\section{Reliable TCP Stream Framing Protocol}
To circumvent TCP's inherent byte-stream nature, we engineered a custom 5-byte length prefix system.

\subsection{Server-side Transmission}
\begin{lstlisting}[language=Python, caption=ServerWorker.py - TCP 5-byte Length-Prefix Framing]
def sendRtpWithTCP(self):
    while True:
        self.clientInfo['event'].wait(0.05) 
        if self.clientInfo['event'].isSet(): 
            break 
            
        data = self.clientInfo['videoStream'].nextFrame()
        if data: 
            frameSize = len(data)
            # 5-byte ASCII size header, zero-padded (e.g. "06742")
            sizeHeader = str(frameSize).zfill(5).encode()
            # Send header + payload atomically
            self.clientInfo['rtpSocket'].sendall(sizeHeader + data)
\end{lstlisting}

\subsection{Client-side Reception}
On the client side, \texttt{Client.py} employs a strict \texttt{recv\_all} loop to guarantee no partial reads occur:

\begin{lstlisting}[language=Python, caption=Client.py - Precise TCP Reception with recv\_all]
def listenRtpWithTCP(self):
    # Client listens; server connects after PLAY
    self.rtpSocket.settimeout(5.0)
    self.rtpConnection, addr = self.rtpSocket.accept()
    self.rtpConnection.settimeout(0.5)
    
    while not self.playEvent.isSet():
        # Read exactly 5 bytes for the length prefix
        length_bytes = self.recv_all(self.rtpConnection, 5)
        if not length_bytes: break
        
        length = int(length_bytes.decode())
        data = self.recv_all(self.rtpConnection, length)
        if not data: break

        with self.bufferLock:
            self.frameBuffer.append(data)
            if len(self.frameBuffer) > 100:
                self.frameBuffer.pop(0)

def recv_all(self, sock, n):
    """Receive exactly n bytes from a TCP socket."""
    data = b''
    while len(data) < n:
        try:
            packet = sock.recv(n - len(data))
            if not packet:
                return None
            data += packet
        except socket.timeout:
            if len(data) > 0:
                continue
            else:
                raise
    return data
\end{lstlisting}
The \texttt{recv\_all} function loops until exactly $n$ bytes have been received. Socket timeouts are handled gracefully: if a partial read has already occurred, the function continues waiting; otherwise, it re-raises the timeout to allow the outer loop to check for \texttt{playEvent}.

\section{Client-Side Jitter Buffer and Render Loop}
The render loop is the heart of the client-side caching system, implementing the consumer side of the producer-consumer pattern:

\begin{lstlisting}[language=Python, caption=Client.py - renderClientBufferLoop (Jitter Buffer Consumer)]
def renderClientBufferLoop(self):
    if self.state != self.PLAYING and not self.isDraining:
        return

    with self.bufferLock:
        # High Water Mark: wait for minBufferSize frames
        if self.isBuffering and not self.isDraining:
            if len(self.frameBuffer) >= self.minBufferSize:
                self.isBuffering = False
            else: 
                self.master.after(40, self.renderClientBufferLoop)
                return

        if len(self.frameBuffer) > 0:
            frame_bytes = self.frameBuffer.pop(0)
            self.updateMovie(self.writeFrame(frame_bytes))
        else:
            if self.isDraining:
                # Buffer fully drained
                self.isDraining = False
                self.state = self.INIT
                self.frameNbr = -1
                if self.pendingPause:
                    self.pendingPause = False
                    self.state = self.READY
                elif self.pendingSetup:
                    self.pendingSetup = False
                    self.state = self.INIT
                    self.chooseQuality()                 
                return
            else:
                # Starvation: re-enter buffering
                self.isBuffering = True

    # Schedule next frame render (~25fps)
    self.master.after(40, self.renderClientBufferLoop)
\end{lstlisting}

Key design decisions:
\begin{itemize}
    \item The render loop uses \texttt{master.after()} (Tkinter's non-blocking timer) instead of a separate thread. This ensures all GUI updates occur on the main thread, avoiding Tkinter's well-known thread-safety issues.
    \item The \texttt{bufferLock} mutex protects the shared \texttt{frameBuffer} list from concurrent access by the network producer thread.
    \item The draining pipeline integrates naturally: when \texttt{isDraining} is true, the buffering check is bypassed, and the loop pops frames until the buffer is empty.
\end{itemize}
